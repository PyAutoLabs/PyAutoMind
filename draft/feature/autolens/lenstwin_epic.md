## Summary

A fitted PyAutoLens lens is already a reloadable generative model (`files/tracer.json` with solved intensities, `image/dataset.fits` with mask, noise map, PSF and over-sampling), the simulator takes any tracer, multi-galaxy and multi-plane are native, and stellar-plus-dark decomposition exists as SLaM model builders — but nothing composes a fit into a simulation with a recorded ground truth, nothing simulates with the observed noise map or a seed by default, there is no instance-level "this light basis at this M/L", and `Basis` has no enclosed-mass route (report §0–§1). LensTwin adds a small `autolens/twins/` subpackage — a frozen `ReferenceModel` (tracer + `ObservationSetup` + provenance), a value-like `Twin` transformed functionally and simulated with a seed, a `TransformationRecord` that states what was requested, how it was normalised and what else changed — plus two PyAutoGalaxy primitives (projected mass inside an aperture for any mass object; light basis → mass basis at a given M/L) and a `MassBudget` convention (report §2). Science lives in ordinary `Science/active` projects that use `al.twins` (ruled 2026-10-28: no dedicated `Science/twins`; built out through use); the workspace and the assistant get examples and a skill only after the workflow has been validated on a real lens (report §2.1, §3 phase 6).

Three invariants: a reference model is immutable and one reference has many twins; preserving any parent property is a recorded choice, never an implicit requirement; every simulated observation carries its ground truth, its transformation chain, its seed and the library versions beside the FITS.

## Original request (2026-10-28; condensed from the brief, section numbering kept — the full text is in the filing session)

> **LensTwin — Building an Observation-Driven Strong-Lensing Simulation Framework**
>
> **1. Context and scientific motivation.** I want to begin developing LensTwin, a new framework within the PyAutoLabs ecosystem for performing scientifically motivated strong-lensing simulations. The central idea is to create digital twins of observed strong gravitational lenses, which can then be modified to answer scientific "what if" questions. This project is motivated by my upcoming ERC Consolidator Grant proposal, which aims to determine whether strong gravitational lensing can measure dark matter density profiles and distinguish dark matter cores from cusps across different galaxy mass scales. However, LensTwin should be designed as a general-purpose scientific framework, not something restricted to dark matter or my ERC application. I envisage LensTwin eventually becoming a resource where researchers can ask questions such as: What if an observed strong lens contained 50% stellar mass and 50% dark matter within its Einstein radius? What if its dark matter halo had an inner density slope of 0 rather than 1? What if its stellar mass distribution had a position angle that twisted with radius? What if the lens contained additional dark matter subhalos or line-of-sight structures? What if we observed the same system with higher resolution or deeper imaging? What if the source galaxy had a different morphology? What if we fitted a complex simulated system using an oversimplified mass model? LensTwin should allow us to construct these experiments using real observed strong lenses as their starting point, simulate the resulting systems, model the simulated observations, and compare the inferred parameters with the known simulation ground truth. Ultimately, I want agentic AI to make this a natural-language scientific workflow. A scientist should be able to describe a "what if" question in natural language, work with an agent to configure an appropriate experiment, and obtain simulation and modelling results that answer that question. The immediate goal is not to build the natural-language interface. It is to establish the scientific and software foundations that make such an interface possible.
>
> **2. The LensTwin philosophy.** Traditional strong-lensing simulations often construct systems by sampling theoretical or empirical distributions of galaxy properties. For example, one might sample stellar masses, halo masses, concentrations, ellipticities and source morphologies before simulating a lens. Such simulations are useful, but it is difficult to ensure they reproduce the complexity of real observed strong lenses. LensTwin instead begins with an observation of a real strong lens that has already been modelled using PyAutoLens. For example, an initial Euclid lens model might contain: an MGE representation of the lens galaxy's light; an SIE mass model with external shear; an MGE source galaxy reconstruction; an alternative pixelized source reconstruction, potentially using a Delaunay mesh; the observational information required to reproduce a realistic simulation, including the PSF, noise characteristics and pixel scale. This observationally inferred model becomes the foundation for a digital twin. The digital twin is not necessarily the true physical representation of the galaxy. Instead, it is an observationally anchored computational representation which retains much of the real system's morphological and observational complexity. We can then modify this twin to investigate specific scientific hypotheses. For example, we could replace the SIE mass model with a stellar mass distribution following the observed MGE light and an NFW dark matter halo. We could construct this new mass distribution such that stars and dark matter each contribute 50% of the projected mass within the original Einstein radius. The resulting modified model becomes the known ground truth for a simulated observation. We can then model the simulated data using PyAutoLens and determine what information we can recover. An important distinction is that LensTwin does not necessarily seek to preserve the observed lensing configuration. We may wish to change the critical curves, image positions, magnifications, shear, source position or even source morphology. Indeed, one observed lens galaxy could provide the foundation for many digital twins with different background sources or physical configurations. Preserving particular observational properties is something we may choose to do for a specific experiment, rather than a universal requirement. However, LensTwin should provide standard and reproducible procedures for normalising physical transformations, particularly when replacing one mass model with another.
>
> **3. The fundamental software concepts.** I envisage LensTwin being built around five concepts. **A. Lens Library** — a collection of observationally inferred strong-lensing models. Each entry should reference an actual observed system and its fitted model, including the components required to generate new simulated observations. The initial library will contain approximately 40 Euclid strong lenses that I will select and model. The library should support metadata and flexible labels, rather than enforcing mutually exclusive lens categories. The initial scientific sample will include: 1. Dwarfs overlapping arcs: typically a more massive primary lens with a lower-mass galaxy whose light overlaps the lensed source. These are systems where the dwarf's gravitational properties may be measurable. 2. Disk lenses: systems with disk-dominated or strongly flattened deflectors. 3. Massive ellipticals: conventional galaxy-scale strong lenses. 4. Multi-galaxy lenses: systems in which multiple galaxies contribute significantly to the lensing potential, including group-scale configurations. These are human-interpretable scientific selections, not rigid object types. A lens might simultaneously be a massive elliptical, a multi-galaxy lens and a system with a dwarf overlapping an arc. The initial models will be prepared separately using existing PyAutoLens modelling workflows. Supporting multiple galaxies is an important early architectural requirement. Both dwarf and multi-galaxy systems involve additional galaxies that must be represented in the observational models, simulations and subsequent inference. We do not need to implement every specialised simulation immediately, but the fundamental LensTwin representation should not assume that every lens consists of exactly one deflector and one source. It should be compatible with different galaxy roles, multiple lens components and, eventually, multiple lens planes where appropriate. **B. Transformations** — the central mechanism through which scientists ask "what if" questions. A transformation modifies some aspect of a digital twin. Examples include: replacing an SIE with a stellar-plus-dark-matter mass model; changing the dark matter inner density slope; adding a dark matter subhalo; adding line-of-sight halos; introducing a stellar mass-to-light ratio gradient; modifying the angular complexity of the stellar mass distribution; changing the background source galaxy; changing an external shear component. Transformations should eventually be composable, enabling multiple physical modifications to be applied to the same observationally anchored system. For example: Observed Euclid lens → stellar + dark matter decomposition → cored dark matter halo → additional substructure. The resulting twin should have a completely defined ground truth. An important design principle is that transformations should explicitly record: the observational model from which they originated; the physical or observational properties being modified; the requested transformation parameters; the mathematical procedure used to construct or normalise the modified model; the resulting ground-truth parameters and model; any additional changes made as part of the transformation. The transformation should also distinguish between requested changes and optional adjustments made to preserve properties of the parent system. Crucially, preserving the original lens configuration should not be an implicit requirement. I think the implementation of generic transformations belongs principally within the PyAutoLens/PyAutoGalaxy source-code ecosystem, rather than being repeatedly implemented in scientific analysis scripts. We need to establish the appropriate division of responsibilities between these packages. **C. Simulation** — given a digital twin, generate a realistic synthetic observation using existing PyAutoLens functionality. The simulator should use the observational setup associated with the parent lens unless instructed otherwise. It should also be possible to simulate the same underlying physical system using different observing configurations. For example, we might use a Euclid lens as our starting point but simulate a deeper observation to investigate whether improved data quality makes the dark matter slope measurable. Simulation outputs should retain the exact generative model and its ground-truth parameters. **D. Inference** — fit simulated observations using PyAutoLens and PyAutoFit. The inference model need not be identical to the generative model. However, an important initial scientific application is investigating whether parameters can be recovered without any model misspecification. For example, to determine whether a dark matter slope is measurable at all, we can simulate and fit using the same stellar-plus-dark-matter profile families. We should not assume that introducing model misspecification is always necessary or more scientifically interesting. There are two distinct questions: 1. Parameter identifiability: can the observations constrain the parameters if the physical model is correct? 2. Model robustness: are those constraints accurate when the modelling assumptions are imperfect? Both are important, but the first is the immediate priority for my ERC work. Later, LensTwin should support experiments where the simulation and inference models intentionally differ. **E. Experiments** — an experiment coordinates the selection of observed lenses, transformations, simulation, inference and comparison with ground truth. For example: "Take ten massive elliptical strong lenses, replace their SIE mass models with stellar MGE plus generalized NFW halos, simulate Euclid observations, fit with the corresponding stellar-plus-dark-matter model, and determine the recovered dark matter slopes." An experiment should record enough information to reproduce and interpret its scientific conclusions. I want this to scale eventually to large samples, parameter grids and repeated noise realizations, including HPC execution. However, we should begin with the simplest possible working experiment.

> **5. Quantifying the effect of transformations.** One important feature I want LensTwin to support is understanding what a transformation actually changes before performing expensive inference. Suppose we begin with an observationally fitted lens and replace its SIE mass model with a stellar-plus-dark-matter model. We should be able to visualise and quantify the differences between the original model and the modified twin. For example: differences in predicted lensed images; differences in deflection fields; differences in critical curves; differences in enclosed mass profiles; differences in convergence or other relevant mass-map quantities. For parametric source models, a useful initial diagnostic would be a noise-weighted comparison of the original model image and the twin model image, evaluated on a common observational grid: Δχ²_image = Σ_i [I_twin,i − I_parent,i]² / σ_i². This provides an initial measure of how substantially the transformation changes the predicted observation relative to its noise. We might also calculate the change in chi-squared relative to the actual observed image, keeping the observational model parameters fixed. These are not necessarily equivalent diagnostics and should be distinguished. A small image difference may suggest that a transformation has little directly observable effect under the chosen conditions. However, this is only an initial intuition, not a rigorous statement about parameter identifiability, which requires inference. We should eventually be able to compare transformations before and after allowing model parameters to readjust. For now, I want the architecture to recognise the distinction between: a transformation's effect on the underlying physical model; its effect on the predicted observation; its effect on the parameters recovered through inference. We do not need every diagnostic implemented in the first phase.

> **6. The first scientific experiment: stellar and dark matter decomposition.** The first major transformation I want to implement after the initial ingestion functionality is: replace an SIE mass model with stellar mass following the observed lens-light MGE plus an NFW dark matter halo. For a simple single-deflector lens, we would: 1. Begin with an observationally inferred SIE mass model and MGE lens light. 2. Calculate the SIE's projected enclosed mass within a defined reference aperture, initially based on the Einstein radius. 3. Construct the stellar mass distribution from the observed lens-light MGE, assuming a constant stellar mass-to-light ratio. 4. Construct an NFW halo. 5. Normalise the two components so each contributes 50% of the projected mass within the reference aperture. 6. Generate a simulated observation using the transformed mass model and an MGE source. 7. Fit the simulation using a stellar-plus-dark-matter mass model. 8. Assess whether we recover the input stellar mass-to-light ratio and dark matter parameters. After establishing that this works, we would fit using a generalized NFW model with a free inner dark matter slope. This allows us to investigate whether the slope is actually constrained by Euclid observations. Eventually, we will vary the injected dark matter slope, mass fraction, source morphology and observational conditions. An important design consideration is that mass normalisation should be explicit and reusable. In particular, the reference aperture, projected mass convention and treatment of individual mass components should be documented. For multi-galaxy systems, the correct normalisation procedure may differ from the single-deflector case, and the framework should not silently assume that one Einstein radius uniquely defines every component's mass. We should design a clear interface now, but do not need to implement every possible normalisation procedure immediately.
