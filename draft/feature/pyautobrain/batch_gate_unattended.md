The four-leg ship gate was designed for runs with a human in the session. Every
leg has an assumption that breaks at 3am. This phase fixes the gate, in doctrine,
before anything is scheduled against it. `Autonomy: human-required` deliberately:
this is a doctrine edit, and doctrine edits are the human's.

## 1. Heart is the problem nobody has costed

Leg 4 requires GREEN or STALE, or a YELLOW "whose reason set is contained in the
set the human acknowledged at launch … any new reason, or RED, parks the run",
and the hard invariant is that YELLOW and RED are "never acknowledged
autonomously". Overnight, nobody can acknowledge anything. So a whole night shift
rides on the reason set staying frozen for fifteen hours.

It does not stay frozen for one afternoon. The log shows a drift count growing
**2 → 4 → 6 across a single day**, re-asked at each ship. It shows a *benign new*
reason appearing mid-session from the run's own sibling merge ("release
validation stale: source moved since rehearsal") — meaning **wave 1 of a batch
can manufacture the reason that parks waves 2 and 3**. And the 2026-07-09
calibration review records that Heart never read GREEN: every shipped run went
out on an acked YELLOW. The base rate says leg 4 blocks by default.

The pressure this creates has already produced a doctrine violation:
`complete/2026/08/cmap-magma-default.md` shipped under a **standing** ack, which
`AUTONOMY.md` explicitly voids ("a stored, reused or 'standing' authorization
does not count — it must be for this RED, now"). Batching will manufacture more
of those unless doctrine moves first, deliberately.

Proposal, to be argued and dated in `AUTONOMY.md`:

- At slot time the human acknowledges a **named reason set for the shift**, with
  the set written verbatim into the batch record.
- A run parks on a new **RED**, or on a new YELLOW reason **whose repo intersects
  the run's own repos**. A new YELLOW elsewhere in the organism does not park it.
- A reason generated by an earlier member of the same batch is named as such and
  does not park later members.
- The grant expires with the shift. It is not standing, and it is not ambient.

## 2. What a batch "launch" is

`AUTONOMY.md`: levels bind "only when the human launches with an explicit
`--auto` … Opt-in per invocation, never ambient: no config flag, no environment
variable, no 'remembered' mode."

A wave firing at 4am under a slot approval given at 17:00 is a stored grant
unless doctrine says otherwise. Define it explicitly rather than letting the
implementation quietly redefine it: **a batch dispatch is one launch**, its
membership fixed at approval, its grant expiring at the end of the shift, its
terms written into `batches/<date>.md` where they can be read afterwards. A
member not dispatched in that shift is not launched — it returns to the queue.

## 3. The adversarial fifth leg

The review leg on autonomous ships is today, in practice, **the branch's own
author**; the organism's own audit
(`complete/2026/08/falsified-by-checkpoint-efficacy-review.md`) found that "a
healthy pass and a rote one write the identical ledger row", and that the one
confirmed-wrong load-bearing claim of its window lived outside the surface the
stage reads — "the stage could not have caught the one escape that actually
happened". The catches that did happen came from *independent* review by a
different model.

So add a fifth leg for unattended ships: an **independent-model adversarial
review**, run in a separate session from the implementer, whose job is to falsify
the run's own claims — starting with its witness. This is the mechanism that
converts human review-minutes into tokens, which is the one currency this epic
has in surplus. It is mandatory for tier `notify` (phase 4) and for anything
launched under the phase 0 autonomy experiment.

Note `ultrareview` exists on this plan (multi-agent verified review in a cloud
sandbox, non-interactive `claude ultrareview --post` for CI, ~500 files / 8,000
lines cap, a few free runs then usage credits). Evaluate it as the implementation
before writing one; the leg is defined by its independence, not by its tooling.

## 4. Decide-and-flag, capped

At a judgement gate an unattended run may, instead of parking, take the more
reversible option and record it — but narrowly, because the agent deciding is the
demonstrably poorest judge of its own decisions' scope. **68 of 332 August
records (20%) carry a CORRECTION or a retraction**, including a record whose own
claim was later marked "FALSE when this record was written". And "reversible" is
the wrong axis: an API-philosophy fork decided on behalf of an external reporter
is trivially reversible in git and irreversible in public.

So:

- **At most one flagged decision per PR.** A second judgement gate parks the run,
  exactly as today.
- The PR body must state the **rejected alternative** and the **one-command
  revert**. If the run cannot write the revert, the decision was not reversible
  and it must park.
- Never available to tier `judge`, and never to a decision touching a public API,
  a default, an error contract, or an external reporter's request.
- The PR carries a `decision-taken` label so the board sorts it above clean work.

## 5. `rejected-at-review`

Add the outcome value `autonomy_log.md` structurally lacks, and require the
**human** to stamp it in the slot. Today a human rejecting a run's recommendation
is logged `amended` and a withdrawn five-PR mechanism was logged `reverted`,
which is why the log reads zero-rejected and why the graduation rule can never
fire in the demotion direction. Without this, phase 0's experiment cannot fail,
and an experiment that cannot fail is not evidence.

Also: rows must be written **per work-type**, since the graduation rule is
per-work-type and the cited 238 is an aggregate.

## Done when

- `AUTONOMY.md` carries all four changes, dated, each citing the evidence above,
  each with an explicit revert condition.
- The fifth leg is implemented and its verdict recorded in the ledger row.
- No mechanism in this phase can be enabled by a config flag or an environment
  variable.
