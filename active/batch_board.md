**Re-scoped by the human 2026-08-31 (see the epic's "Development through use"
section): not a second published surface.** The batch state is a strip on the
Mind dashboard, placed **above the "Start here" section** — the first thing the
human sees when they open the dashboard. The original standalone-board scope is
recorded in the epic and closed; do not rebuild it.

## What the strip renders

A single compact "Batches" block, generated by the same collect the dashboard
already runs (`_intake.py` — the markdown section builder near the "## Start
here" emit at `agents/conductors/intake/_intake.py:2027` and its HTML twin at
`:2325`; the strip is emitted immediately before both):

- **Latest packet** — link to the newest `batches/packets/<date>-<slot>.html`
  (the Pages URL `https://pyautolabs.github.io/PyAutoMind/packets/…`), with its
  `generated:` stamp.
- **Review state** — whether `batches/reviews/<date>-<slot>.md` exists for that
  packet: `review submitted` or `awaiting your review`.
- **In-flight batch** — if the newest batch record has no `collected:` yet: its
  member count, `review-at:`, and a PENDING note.
- **Archive** — one link to `batches/packets/` (the history).

Pure render over files that already exist; it decides nothing and recomputes
nothing. Every chip routes to the packet, the review file, or the batch record.

## Widened 2026-09-02 — both dashboards, and the science board goes live

Human's request, verbatim:

> I would like each dashboard to have a batch status box at the top, which basically has
> information in if a batch + review job is on going, it list all tasks as one line, and
> states whether they are in progress or awaiting review. When we are ready to review a
> button with the review URL link should be provided on the dashboard.
>
> For the PyautoMind development batch work, it is normal to wait for the full batch to be
> complete and then review in one go. This should be the default and dont change the
> behaviour.
>
> For the PyAutoCortex science batch work, I don't think we should be so constrained. Some
> science runs can take hours, others may take days. Instead, it should basically be that
> the review is live whenever anything can be reviewed, and when a task is completed is it
> added to the existing review board. WE should not be able to review something which is
> mid flight, this is more so that we can review stuff more on the fly if I want. The
> dashboard status thing here is thereofre more important as it shows all live information
> on how progress of science runs are going.

What this adds to the strip above:

- **One shared status computation** (`PyAutoBrain/agents/conductors/batch/_status.py`,
  stdlib only — the Cortex renders in a Pages job with no pip install) that both
  `_intake.py` and `_cortex.py` draw from, markdown and HTML twins alike: the open slot
  (latest `dispatched:` among open records — never lexical), one line per member with
  *in progress* / *awaiting review* / *ruled*, and the Pages packet URL
  (`https://pyautolabs.github.io/<Organ>/packets/<slot>.html`) as a button once there is
  something to review. Nothing open renders the fixed fixture "No batch in flight".
- **Mind rule (unchanged behaviour):** the button appears once `collected:` is stamped;
  before that the box says in flight, review at `review-at:`.
- **Cortex rule (rolling):** the button appears as soon as one member is
  `awaiting-ruling`; `submitted`/`running` members show as in progress with wall vs budget
  and last refresh, and hold no review control. A slot **stays open across partial
  reviews** — a later review lands as `batches/reviews/<slot>-r<N>.md` (append-only),
  `batch collect --kind cortex` keeps refreshing the packet while anything is on the board,
  ruled members are never re-spliced, and the slot closes when nothing is left in a board
  state. `cortex.py check`/`rule` accept the numbered files.
- `PyAutoMind/.github/workflows/dashboard_refresh.yml` triggers on `batches/**` (the
  Cortex workflow already does).

Merge order: PyAutoCortex (check accepts `-r<N>`) → PyAutoBrain → PyAutoMind.

## Not in scope

Review actions (merge/tweak/reject live on the packet page and in the
orchestrator chat), gate-leg rendering, usage-window readings, any scheduled
pre-slot publish. If the strip ever needs its own collect, that is the
`batch collect` verb's job, not the dashboard's.

## Done when

- Both dashboards (markdown and HTML) open with the status box, correct with
  nothing open (fixture), with an in-flight batch, and with a reviewable one
  (button present); the Cortex box shows a mixed running/awaiting board with the
  button live and running members without review control.
- A second partial Cortex review file refreshes the packet without touching
  earlier member sections, and `cortex.py check` stays clean.
- Regen is idempotent and the existing dashboard tests pass.
